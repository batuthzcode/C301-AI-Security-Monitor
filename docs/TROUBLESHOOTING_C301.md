## DEBUG FIX #001 — User-observed YAML list workaround

### Before

- Device was discovered in the Xiaomi Home **Singapore** server region (Europe did not list it).
- The live video became accessible through go2rtc; Administrator execution was **not** required.
- Earlier `read udp ... i/o timeout` required local connection troubleshooting. Changing the Windows network profile from Public to Private alone did not solve that issue; a scoped inbound UDP firewall exception and reconnect attempts were also tried. The independent effect of each change remains unverified.
- During streaming, go2rtc logged `miss: read media: cs2: pop buffer is full` roughly every 11–12 seconds.

### User's reported adjustment

The user restored a previously working backup and changed the `c301` source into a YAML **list item**, using a leading `-`, without quotes. They also reported `subtype=auto` and `audio=0` parameters. Following this adjustment, the recurring CS2 warning was **not observed in the initial check**.

Safe **illustrative structure only** (NOT a runnable camera address):

```yaml
streams:
  c301:
    - xiaomi://PRIVATE_CAMERA_SOURCE?model=mxiang.camera.c301&subtype=auto&audio=0
```

This example deliberately omits a functioning URL; preserve the full private source generated by go2rtc. Do not publish `go2rtc.yaml` or any backup.

### Assessment

- In YAML, `-` denotes a list item. go2rtc can receive stream-source lists.
- Quotes surrounding a valid YAML string do not themselves change the source URL.
- Because the backup, source representation, and/or stream options varied across attempts, it is **not established** that the leading hyphen fixes the upstream CS2 problem. This is an **observed, reproducible-to-be-tested workaround**, not a confirmed permanent solution.
- Absence of warnings is meaningful only while a video consumer is **actively connected**. Test 5–10 minutes of continuous playback and watch for image artifacts or dropped frames.

### Rollback

1. Stop go2rtc and RTSP viewers.
2. Replace the active private `go2rtc.yaml` with the saved working backup.
3. Restart go2rtc, confirm `c301` exists, and retest the live feed.
4. Never commit either private file.

## DEBUG INVESTIGATION #003 — HEVC errors after RTSP-over-TCP test (OPEN)

**Observed on Windows (2026-10-26):** The Python/OpenCV preview started through
`rtsp://127.0.0.1:8554/c301`. The user set
`OPENCV_FFMPEG_CAPTURE_OPTIONS=rtsp_transport;tcp` for RTSP transport to go2rtc.
Nevertheless the decoder printed:

```text
[hevc] Could not find ref with POC 32
[hevc] The cu_qp_delta 29 is outside the valid range [-26, 25].
```

**Interpretation:** FFmpeg's H.265 decoder could not find a reference picture
and rejected an invalid QP delta. These symptoms are consistent with invalid
or missing video data but do **not** prove whether corruption originates in the
C301, Xiaomi CS2 transport, go2rtc restreamer, RTSP transfer, or decoder. A
single startup warning while video stabilizes differs from persistent warnings
accompanied by frozen/corrupted frames.

**Important distinction:** Forcing TCP on the RTSP/OpenCV client controls only
the **go2rtc → Windows Python** segment. It does not force TCP on the separate
**camera → go2rtc** CS2 connection.

**Next safe, controlled check:**

1. Leave the currently working private `go2rtc.yaml` unchanged if video has no
   visible artifacts; keep the preview open 5–10 minutes and note whether errors
   are only at startup or continuously recur.
2. If errors recur and video freezes, make a new private backup of the working
   YAML. For only the `c301` source URL, replace an existing `subtype=auto` with
   `subtype=sd` (go2rtc officially documents `sd`); do **not** add a duplicate
   `subtype` parameter. Preserve the leading YAML list item `-` and all private
   account/device parameters exactly. Save/restart go2rtc, then test 5 minutes.
3. If the lower-quality stream is no better, restore the saved working YAML.
   A later separate test could change the Xiaomi/CS2 transport setting; do not
   mix several changes in one trial.
4. Avoid muting decoder errors as a substitute for validating frame integrity.
   Never upload config contents, log lines with private URLs, or device IDs.

**State:** unresolved. No firmware or Python application source was modified.

## Debug Fix #005 — go2rtc `unsupported scheme` after adding H.264 stream (2026-10-26)

**User report:** go2rtc MSE preview emitted `streams: unsupported scheme` while
the apparent source contained both a leading dash/quote before `xiaomi://`
and a literal `c301_h264:` configuration fragment. The source was not
parsed as two valid named YAML streams. **This is a configuration-format
error, not proof of an FFmpeg decoder issue.**

**Correct structure (EXAMPLE ONLY: placeholders are not runnable):**

```yaml
streams:
  c301:
    - "xiaomi://PRIVATE_SOURCE_URL_WITH_ALL_EXISTING_PARAMETERS"
  c301_h264:
    - "ffmpeg:c301#video=h264"
```

The real full `xiaomi://` URL must stay in the user's private configuration
and must **never** be pasted into public documents. The indentation is exact:
`streams` at column 1, stream names at two spaces, a hyphen **and a space**
for each source at four spaces. The `-` is YAML list syntax, **not** part of
the URL. In particular, `-"xiaomi://..."` without a separating space is
not the intended YAML list-item format. The H.264 stream must be a separate
sibling of `c301`, not appended to the camera URL. Keep all other go2rtc
sections unchanged; define `streams:` only once. Edit in WebUI **Config** or
the real private `go2rtc.yaml`, NOT in the Temporary stream URL field.

**Verify:** back up config, save/restart go2rtc, then confirm separate
`c301` and `c301_h264` entries; inspect `c301_h264` in browser, then retry
`rtsp://127.0.0.1:8554/c301_h264` in Python. FFmpeg must be installed and
visible in go2rtc's PATH (restart go2rtc after installing FFmpeg).

**Status (user verified, 2026-10-26):** After the user corrected the quotation
marks surrounding the source definition in the private YAML, the go2rtc UI
successfully displayed live video from **both** `c301` and `c301_h264`.
Thus the previous `unsupported scheme` failure is **resolved for go2rtc browser
playback**. The exact previous malformed text has not been independently
reproduced, so the documentation does not claim the quotation marks are a
universal fix. Whether the **Windows Python/OpenCV** application now displays
valid H.264 frames instead of green or no video is **not yet verified**.
No changes to camera firmware or Python application code.

## Milestone 018 — Local RTSP client abort (`WSAECONNABORTED`)

**Symptom**

```text
WRN internal/rtsp/rtsp.go:262 > error="read tcp 127.0.0.1:8554->127.0.0.1:<ephemeral-port>: wsarecv: An established connection was aborted by the software in your host machine."
```

The endpoints are both `127.0.0.1`, making this a *local RTSP consumer/session* event rather than proof of a failed camera LAN connection. Microsoft's Winsock documentation classifies the text as **WSAECONNABORTED / 10053**. The log is not equivalent to the upstream Xiaomi `cs2: pop buffer is full` error.

**Non-invasive isolation plan**

1. Record whether the warning appears **only when the Windows Python app or FFmpeg viewer exits**, or continuously while a preview is open. A one-time warning during shutdown may be benign.
2. Keep `go2rtc.yaml`, Xiaomi tokens, and camera firmware unchanged. Restart no software unless necessary; do not globally disable Windows Firewall.
3. From a *new PowerShell window* with installed FFmpeg/FFprobe in PATH, test the local H.264 RTSP stream independently of Python:

   ```powershell
   ffprobe -v error -rtsp_transport tcp -select_streams v:0 -show_entries stream=codec_name,width,height -of default=noprint_wrappers=1 "rtsp://127.0.0.1:8554/c301_h264"
   ```

4. Play the same stream with FFplay:

   ```powershell
   ffplay -rtsp_transport tcp -i "rtsp://127.0.0.1:8554/c301_h264"
   ```

5. Compare outcomes:
   - **FFplay works; Python fails:** investigate OpenCV capture lifecycle and decoder path.
   - **Both fail but go2rtc browser works:** inspect FFmpeg restream/transcoder process, startup order and go2rtc console for command errors.
   - **Both work; one warning occurs on viewer closure:** likely a session shutdown event; monitor without modifying the camera config.

**Not yet resolved:** Stable transcoded H.264 in the Python application has not been demonstrated.

- https://learn.microsoft.com/en-us/windows/win32/winsock/windows-sockets-error-codes-2
